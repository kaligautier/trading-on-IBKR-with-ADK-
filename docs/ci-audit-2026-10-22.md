# CI audit and recommendations

Date: 2026-10-22. Scope: GitHub Actions, dependency updates, merge protection,
and release controls for this repository.

## Assessment

The CI already has useful functional and security checks and reasonable execution
times. The highest priority is to make those checks enforceable before merging:
the branch protection inspected during the audit required only `PR size` and
`PR component scope`, rather than application tests, builds, or dependency audits.

This is an evidence-based audit and a proposed improvement plan. It does not
change workflows or repository settings, or certify the deployed applications.

## Existing strengths

- Workflow actions are pinned to commit SHAs, with generally read-only token
  permissions and short-lived OIDC authentication scoped to Scanner publication.
- Python and npm dependencies are locked. Runtime dependency audits, container
  builds, and smoke tests already cover important failure modes.
- PostgreSQL/Liquibase integration tests and the Scanner-to-Reader schema check
  provide stronger evidence than unit tests alone.
- Secret scanning, push protection, and Dependabot security updates were enabled.
- Branch protection enforced administrators, disallowed force pushes and branch
  deletion, required an up-to-date branch, and required conversation resolution.
- The `pull_request_target` policy workflows check out trusted default-branch
  validators, disable credential persistence, and read PR metadata rather than
  executing proposed code. Preserve this trust boundary.
- The frontend deployment guide documents rollback by restoring the previous
  image digest through a reviewed Terraform plan.

These controls align with GitHub's [secure workflow guidance](https://docs.github.com/en/actions/reference/security/secure-use).

## Prioritized recommendations

### P0: require functional and security checks before merging

**Observed:** only `PR size` and `PR component scope` were required on `main`.
No additional rulesets were returned. Application or security failures therefore
did not themselves prevent merging under the inspected configuration.

**Recommendation:** add a stable, mandatory `CI required` check while retaining
the existing policy checks. Run its workflow on every PR and select component
jobs inside the workflow. The final job should use `always()` with explicit
dependencies, then validate each result against the detected change scope.

Accept skipped component jobs only when the component is unaffected. Fail when
a required job fails, is cancelled, is unexpectedly skipped, or scope detection
fails. Do not assume that a skipped dependent job blocks a merge.

Do not simply require every existing path-filtered workflow: an untriggered
workflow can leave a required check pending indefinitely.
See [GitHub's required-check guidance](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks).

**Acceptance:** a deliberately failing application test prevents merging;
documentation-only PRs pass; database changes select every affected consumer;
cancellation or scope-detection errors cannot produce a successful final check.

### P1: make domain integration coverage continuous

**Original finding:** Scanner CI selected only unit tests. The Reader domain
integration test was skipped unless `RUN_DOMAIN_TESTS=1`, so its presence in the
repository did not prove execution in the inspected workflows.

**Update:** the documentation preparation snapshot adds
[`domain-database.yml`](https://github.com/kaligautier/trading-on-IBKR-with-ADK-/blob/7949165d1f17dd5d4e629b5f5f249fe047e29402/.github/workflows/domain-database.yml),
which invokes `database/scripts/rehearse_domains.py` on matching PR changes or
manual dispatch. This partially addresses the original finding. It has no
`push` trigger for `main` in that snapshot.

**Recommendation:** retain the rehearsal, inspect its executed tests and skip
counts, include it in the required gate for database and application changes,
and add verification after merging to `main`.

**Acceptance:** the rehearsal proves real migrations, report persistence and
reading, restart behavior, and restricted database permissions. Missing fixture
configuration must fail the dedicated integration job rather than skip its
required tests.

### P1: verify lockfile freshness consistently

**Observed:** Momentum explicitly runs `uv lock --check`, while Scanner and
Reader rely on `uv sync --frozen`.

**Recommendation:** use `uv sync --locked`, or run `uv lock --check` before frozen
installation for every Python project. Frozen installation consumes the existing
lockfile without checking whether project metadata changed.
See [uv locking and syncing](https://docs.astral.sh/uv/concepts/projects/sync/).

**Acceptance:** changing dependency requirements without updating `uv.lock` fails
CI before application tests run.

### P2: complete dependency and security coverage

**Observed:** Dependabot configuration omits Momentum's Python project, the
frontend Dockerfile, and Terraform roots including `infra/momentum`,
`infra/frontend`, and `infra/frontend/build`. GitHub CodeQL default setup reported
`not-configured`; no CodeQL workflow was present in the inspected source.

**Recommendation:** cover the missing manifests and image directories, group
compatible updates within each component, and add Python, TypeScript, and Actions
code scanning. Add workflow validation with actionlint. Keep dependency audits
alongside static analysis: they detect different classes of problems.

**Acceptance:** every maintained manifest is covered by an update configuration;
analysis runs for relevant PRs and periodically on `main`.

### P2: distinguish an executed audit from an intentionally skipped audit

The [LiteLLM run 39829555255](https://github.com/kaligautier/trading-on-IBKR-with-ADK-/actions/runs/39829555255)
succeeded, but its package-audit step was skipped because the selected changes
did not affect LiteLLM infrastructure. That success does not prove the findings
from [failed audit 39552348762](https://github.com/kaligautier/trading-on-IBKR-with-ADK-/actions/runs/39552348762)
were fixed. Its logs reported vulnerabilities in `aiohttp` and `certifi` in both
audited images; these are historical findings, not a fresh scan of current images.

**Recommendation:** preserve the daily image audit already configured on `main`.
Publish reports as workflow artifacts even when audits fail, and make summaries
explicit about execution, scope, image digests, and the latest completed audit.
Keep independent audits for application locks and installed container packages.

**Acceptance:** each image-security claim links to an executed audit of the exact
digest being released; scoped skips cannot be mistaken for a clean scan.

### P2: formalize publication and deployment controls

**Observed:** the Scanner publication job references `scanner-release`, but the
GitHub environments API returned no configured environments. A name in YAML alone
does not establish approval or branch restrictions. Publication also rebuilds
the image after the earlier image job, then smoke-tests that new image.

**Recommendation:** configure release environments explicitly, restrict permitted
branches, and define approval requirements appropriate to the project. Publish
and promote the same verified image digest. Link commit, checks, digest,
deployment verification, and rollback target in a release record. Add provenance
and SBOM attestations for published artifacts when the release path is established.

**Acceptance:** publication requires the selected gates; deployment uses the
verified digest; post-deployment checks verify real behavior; rollback restores a
previous digest through the documented infrastructure workflow.

References: [GitHub deployment environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)
and [artifact attestations](https://docs.github.com/en/actions/concepts/security/artifact-attestations).

## Suggested delivery order

1. Add and require the aggregate CI gate; prove failure and documentation-only cases.
2. Integrate the domain database rehearsal into that gate and post-merge checks.
3. Enforce lock freshness and complete Dependabot coverage.
4. Add code/workflow scanning and retain audit artifacts.
5. Establish protected release environments and promotion by immutable digest.

Prioritize enforcement and coverage before further performance work: the measured
workflows are already short enough that speed is not the main limitation.
